# ADR 0001: the Luau API registry is parsed from `docs/spark.d.luau`

**Context.** The API was described three times by hand (`SPARK_API.md`, `spark.d.luau`, Rust). They drifted (e.g. `test.texts` was missing from the types).
**Options.** (a) Rust macros that register every function and generate docs; (b) keep the typed definition file as the one source and parse it; (c) generate definitions from the VM at runtime.
**Decision.** (b). `docs/spark.d.luau` already is a complete, typed, human-reviewed signature list that luau-lsp consumes. `crates/spark-api` parses it into a registry and generates `docs/API_REFERENCE.md`, `docs/api.json`, `llms.txt` and `spark api search`. Two tests close the loop with the engine: `spark-api/tests/generated.rs` (generated files are current, the guide mentions every global) and `spark-script/tests/api_drift.rs` (every documented function/table/class member exists in a running VM; every VM global and table member is documented; the `test` table is checked inside a scenario test).
**Consequences.** Adding an API function = edit `spark.d.luau` (+ a doc comment), run `SPARK_BLESS=1 cargo test -p spark-api`. Methods of userdata classes cannot be enumerated at runtime, so the reverse check (undocumented method) only covers plain tables. Per-function units, limits and examples are free text in the doc comments for now; structured fields are future work.

**Amended by [ADR 0004](0004-type-registry-reflection.md).** The component/property blocks of `spark.d.luau` (`Object` fields, `SpawnProps`, `BodySpec`, `LightSpec`) become generated from the reflection registry; functions, globals and namespaces stay hand-written here.
